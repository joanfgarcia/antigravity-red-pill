### 🔥 Daemon: mecanismo de CPU → GPU recovery (FALTA)

- [ ] **El daemon no vuelve a GPU tras caer a CPU**. En `run_dual_bind.py:104`:
  ```python
  if self.mode is not None:
      return  # ← bloqueado para siempre
  ```
  Una vez establecido `mode = "cpu"`, no hay re-evaluación. Si matas el
  CPU worker scope mientras está activo, todas las requests devuelven
  500 (URLError: Connection refused). Sólo `systemctl restart
  redpill-llm.service` lo recupera.
- [ ] **El CPU worker scope sobrevive al restart del daemon**. `_start_cpu_worker`
  lanza vía `systemd-run --user --scope --unit=redpill-cpu-worker-8761.scope`.
  Al restart del service, systemd mata el main pero NO el scope unit.
  Hay que matarlo manualmente: `systemctl --user kill
  redpill-cpu-worker-8761.scope`.
- [ ] **Diseñar e implementar mecanismo CPU → GPU**:
  - Opción A: TTL-driven re-evaluación. Si `mode == "cpu"` y han pasado
    >N minutos sin requests, intentar GPU de nuevo. Si falla, vuelve
    a CPU.
  - Opción B: VRAM-driven re-evaluación. Antes de cada request, leer
    VRAM libre. Si cabe un GPU tier, switch transparentemente.
  - Opción C: watchdog daemon que periodically (cada 5 min) verifica VRAM
    y trigger `mode = None` si GPU vuelve a estar disponible.
- [ ] **Telemetry**: el daemon no expone qué `mode` está activo en `/health`
  ni `/v1/models`. Sin esto, el healthcheck externo no puede detectar
  degradación.
