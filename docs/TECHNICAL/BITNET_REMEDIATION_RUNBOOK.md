# RUNBOOK: BitNet CUDA Remediation (RTX 5070)

> **Documento complementario**: Para la documentación exhaustiva del pipeline de pesos
> (bit-shifts, permutaciones WMMA, kernels CUDA), ver [BITNET_WEIGHT_PIPELINE.md](./BITNET_WEIGHT_PIPELINE.md).

## Contexto Técnico
El sistema BitNet 1.58b utiliza una representación ternaria de pesos. En la RTX 5070, la inferencia estaba produciendo ruido incoherente debido a que los kernels de dequantización específicos para la arquitectura de GPU estaban en estado de placeholder (vaciados durante una limpieza anterior o mala sincronización de rama).

## El Fallo: "The Silent Placeholder"
En `3rdparty/BitNet-1.58b/3rdparty/llama.cpp/ggml/src/ggml-cuda.cu`:
- El kernel `k_bitnet_porter` solo realizaba una copia de bytes: `dst[i] = src[i]`.
- Al no dequantizar los valores ternarios empaquetados, la multiplicación de matrices (GEMM) recibía basura lógica, resultando en el output `ivi...`.

## Remediación Aplicada
1. **Restauración del Porter**: Se implementa la lógica de dequantización real en `bitnet_cuda_porter_axon` para mapear los pares de bits `00, 01, 10` a los valores flotantes `-1.0, 0.0, 1.0` multiplicados por el `block_scale`.
2. **Forzado de Backend**: Se ajusta `providers.py` y el entorno de build para que `GGML_BITNET_FORCE_AXON=CUDA` sea la ruta por defecto en hardware NVIDIA.
3. **Sincronización de Tipos**: Se asegura que `block_i2_s` mantenga el tamaño de 36 bytes (32 bytes de pesos + 4 bytes de escala float) para alinearse con el formato de disco de los modelos Falcon 3 V2.

## Cómo verificar la estabilidad
Ejecutar el benchmark soberano:
```bash
python scripts/bitnet_sovereign_bench.py --flavor CUDA
```
El reporte debe mostrar > 15 t/s y coherencia gramatical en la RTX 5070.

## 4. CUDA Inference Anomaly: The "Phantom Kernel Hijack"
### 4.1. Incident Description
During cross-platform validation, the NVIDIA RTX 5070 (CUDA) backend produced silent, empty string responses (`...`) at high speeds (20 t/s), while the AMD Ryzen AI iGPU (ROCm) generated coherent, mathematically sound text outputs. The identical C++ dequantization logic (`dequantize.cuh`) applied to both platforms mathematically verified that the `I2_S` bit-shifting was correct, narrowing the failure solely to the CUDA execution pipeline.

### 4.2. Root Cause Analysis
Initial hypotheses focused on potential hardware precision truncation via Tensor Cores (TF32). However, historical code review revealed a routing hijack introduced during the "Phase 3 Sovereign Porter" feature integration.
1. The codebase registered `GGML_TYPE_I2_S` for hardware-accelerated MMQ (Matrix Multiply Quantized) in `mmq.cu`.
2. This routed tensor evaluations away from the standard `cublasSgemm` pathway to a specialized kernel: `bitnet_mul_mat_ladder_axon` located in `bitnet_porter.cu`.
3. This specialized kernel was merely an empty placeholder (stub) intended for future optimization, leaving output memory uninitialized or zeroed.
4. **Platform Discrepancy**: The NVIDIA Turing/Ada architecture satisfied the condition `int8_mma_available(cc)`, executing the empty MMQ stub. Conversely, the ROCm architecture bypassed this MMQ condition, seamlessly falling back to `to_fp32` desquantization mapped to `hipblasSgemm`, which natively processed the tensors.

### 4.3. Remediation Strategy
To ensure immediate parity and operational stability, the MMQ registration for `GGML_TYPE_I2_S` must be removed from `ggml_cuda_should_use_mmq` within `mmq.cu`. Disabling this incomplete hook forces the CUDA backend to utilize the heavily validated `to_fp32` fallback mechanism alongside `cublasSgemm`, precisely matching the operational logic of the ROCm and NPU backends without precision loss.

## 5. Model Weights Incompatibility: The "Third-Party GGUF Trap"
### 5.1. Incident Description
While attempting to load pre-quantized 1.58b models from third-party HuggingFace repositories (e.g., `israellaguan/Falcon3-10B-Instruct-1.58bit-i2_s`), the `llama-cli` binary consistently failed with an immediate `std::runtime_error`: `"data is not within the file bounds, model is corrupted or incomplete"`.

### 5.2. Root Cause Analysis
The model sizes and checksums were perfectly intact (e.g., exactly 3.99 GB). However, the metadata offsets generated by older or external forks of the `BitNet` compiler differ structurally from our active `ggml.c` definition of `GGML_TYPE_I2_S` (which calculates 36 bytes per 128 elements block, including the 4-byte float scale). Because our binary expects slightly different block paddings than what is embedded in the third-party `.gguf` file header, the cumulative byte calculation exceeds the physical file limit around layer 9 (`blk.9.attn_v`), triggering the bounds-checking safeguard.

### 5.3. Remediation Strategy
**Never rely on pre-compiled third-party `.gguf` files for `I2_S`**. 
To guarantee structural alignment between the model weights and the active execution engine, the model **must be locally quantized**.
1. Use the native `setup_env.py` script provided in the `BitNet-1.58b` repository.
2. Download the official, unquantized (`bfloat16`) base weights directly from the creator (e.g., `tiiuae/Falcon3-10B-Instruct-1.58bit`).
3. Allow the script to dynamically compile the local `llama-quantize` binary, converting the raw weights to `f16` and subsequently into the properly aligned `I2_S` representation tailored to the current environment.

**Execution Command:**
```bash
./venv/bin/python setup_env.py --hf-repo tiiuae/Falcon3-10B-Instruct-1.58bit -q i2_s
```
